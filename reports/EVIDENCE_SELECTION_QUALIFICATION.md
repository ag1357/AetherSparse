# AetherSparse evidence-selection qualification

## Decision

`REAL_CORPUS_ARCHITECTURE_FAILED`

The frozen real-corpus architecture does not meet the evidence-selection
qualification thresholds. The compact reranker improves retrieval, but not
enough to qualify the system. Gap-triggered traversal does not improve the full
held-out result and is removed from the recommended runtime configuration.

## Held-out 10k evidence

The evaluation used the frozen 10,527-document, 220,378-chunk corpus and all
2,000 frozen questions. The question artifact SHA-256 is
`77565d8fa6416a11ed3e5079c173e6d14348836162782699543a3608d0ba440a`.

| System | Article recall@8 | Span recall@8 | Hard article recall | p95 latency | Mean source bytes |
|---|---:|---:|---:|---:|---:|
| Static lexical top-k | 79.65% | 78.45% | 70.22% | 476.3 ms | 1,854 |
| Deterministic rank fusion | 83.00% | 82.10% | 74.57% | 476.3 ms | 1,932 |
| Compact int8 reranker | **84.10%** | **83.30%** | **76.22%** | 476.3 ms | 1,914 |
| Gap-triggered traversal | 84.05% | 83.25% | 76.14% | 547.4 ms | 1,916 |
| Constrained extractive answer path | 84.05% | 83.25% | 76.14% | 547.5 ms | 1,916 |

The best hard-subset gain over static retrieval is 5.93 points, below the
required 10 points. Article and span recall remain below 90%. Targeted traversal
activates on 29.75% of questions, is slightly worse than reranker-only recall,
and increases p95 latency by 14.9%. It is therefore not justified.

The current answer gate is also not a verified RAG system: among emitted
answers, its measured unsupported-answer rate is 15.42% and silent wrong-entity
rate is 14.45%. It must be described as a failed constrained extractive
prototype, not a qualified verified RAG.

## Compact model

The separately trained pairwise linear reranker has 15 parameters, 18
serialized int8 bytes, 14 MACs per candidate, and about 874 MACs per query.
Training used 300 development questions on the separate 1k corpus; 295 had gold
evidence in the bounded candidate pool. The training artifact records 2,360
pairs and all requested hard-negative families.

The model is computationally negligible compared with candidate generation.
This means an NPU cannot credibly improve end-to-end latency.

## Scaling

The same 300-question scaling artifact was run against the already-frozen
packs. No corpus was enlarged.

| Pack | Documents | Reranker article recall | Reranker span recall | Reranker p95 | Mean selected bytes |
|---|---:|---:|---:|---:|---:|
| 1k | 1,163 | 94.00% | 93.67% | 46.4 ms | 2,092 |
| 10k | 10,527 | 88.33% | 88.00% | 570.8 ms | 2,036 |
| 50k | 51,040 | 86.67% | 85.67% | 1,750.7 ms | 2,000 |

Source payload is bounded and does not grow with the corpus. Recall nevertheless
degrades 7.33 article points from 1k to 50k, while candidate-generation p95
grows 37.9 times. The host saw 587,186,176 physical read bytes across the 300
50k queries after cache advice. Python's bundled SQLite driver does not expose
logical page-read counters, and `posix_fadvise` cannot guarantee eviction from
all caches; those two measurements remain explicitly limited.

## Falsification and data limitations

- The compact reranker is useful as an experiment but is not justified as a
  qualified architecture because it misses the absolute recall floors.
- Targeted traversal is rejected because it adds latency without recall.
- The constrained answer path is rejected because verification does not hold
  unsupported and wrong-entity outputs below 1%.
- The frozen 2,000-question set is graph-derived and generated by the existing
  authoring pipeline. It is not sufficient evidence for the requested claim of
  independently authored, natural-language hidden evaluation. No such claim is
  made.
- Actual SQLite physical page traffic on target media, board power, and board
  latency remain unmeasured.

## Hardware digital twin update

The measured host workload is dominated by SQLite/FTS candidate generation and
storage access, not the 874 neural MACs/query. Core1106 is therefore not
justified. eMMC may be relevant to the observed cold-cache traffic, but the host
measurement is insufficient to prove that physical storage is the limiting
target-device component. P4 Pico is not recommended while the architecture
fails accuracy and scaling thresholds. FPGA work remains premature because the
winning retrieval kernel is not stable.

Current hardware action: make no purchase and continue architecture-level
evidence-selection research only if the project is reopened with a different
candidate-index design.

## Reproduce

```bash
uv sync --extra dev

uv run aethersparse selection train \
  --corpus data/real_corpus/simplewiki-1k.sqlite \
  --questions data/real_corpus/scaling_questions.json \
  --output-model data/models/evidence_reranker.int8.json \
  --output-manifest data/models/evidence_reranker.training.json

uv run aethersparse selection evaluate \
  --corpus data/real_corpus/simplewiki-10k.sqlite \
  --questions data/real_corpus/questions.json \
  --model data/models/evidence_reranker.int8.json \
  --output reports/EVIDENCE_SELECTION_10K_FULL.json

uv run aethersparse selection evaluate \
  --corpus data/real_corpus/simplewiki-1k.sqlite \
  --questions data/real_corpus/scaling_questions.json \
  --model data/models/evidence_reranker.int8.json \
  --output reports/EVIDENCE_SELECTION_SCALE_1K.json

uv run aethersparse selection evaluate \
  --corpus data/real_corpus/simplewiki-10k.sqlite \
  --questions data/real_corpus/scaling_questions.json \
  --model data/models/evidence_reranker.int8.json \
  --output reports/EVIDENCE_SELECTION_SCALE_10K.json

uv run aethersparse selection evaluate \
  --corpus data/real_corpus/simplewiki.sqlite \
  --questions data/real_corpus/scaling_questions.json \
  --model data/models/evidence_reranker.int8.json \
  --output reports/EVIDENCE_SELECTION_SCALE_50K.json

uv run pytest -q
uv run ruff check src tests
uv run mypy src
uv run aethersparse serve --host 0.0.0.0 --port 8000
```

Open `/` on the service from an Android browser. The UI calls
`POST /v2/selection/query`; it never calls the selector in-process.
